# Installer integrations

The user approved an installer-backed integration after testing repeat installation.
Keep the service global, adopt existing installations, and index a project when
it selects the integration. Do not upgrade or uninstall a shared service as a
side effect of project reconciliation.

## Approach

Use `installer: codebase-memory` on an item or harness override. The first supported
adapter invokes the installed `codebase-memory-mcp` CLI, not catalog shell scripts.
A missing executable produces exit 3 with upstream installation instructions.
Native plugin repackaging was rejected as too complicated. An unrestricted command
runner would need an asset/ownership protocol; defer that until another installer
requires it.

Run configuration-only installation in a temporary HOME with explicit client
directories, `--skip-binary`, and `--dir` pointing at the existing executable.
Import the upstream skill, agent profiles and hooks into project-owned destinations.
Derive the MCP server as an ordinary artifact so regeneration and launch retain it.
Keep the runtime's normal per-user cache and service. Never run global installation,
update, uninstall, or change automatic-indexing settings.

Use an ignored local receipt under `.loadouts/installers/` for owned file hashes,
hook entries, executable identity and successful indexing of this absolute project
root. Protect user modifications and unrelated hooks. Repeated installation should
leave files unchanged; missing files are restored. A failed index remains retryable.
Record observed installer versions in the project lock (v5, older locks readable).
Different users can have different versions; the shared service remains best effort.

Selecting the integration adds `installer:<harness>:codebase-memory` and
`mcp:<harness>:codebase-memory-mcp`. Deselecting removes only owned project
configuration, retaining the global executable, daemon and index. Multiple selected
items share the integration. `doctor` and launch detect missing local assets.

## Evidence and constraints

Native 0.12.1 installation with a temporary HOME changed no generated bytes on a
second run. `--skip-binary` avoids session shutdown. This release needs the
explicit executable directory and conventional `.codex`/`.claude` staging markers.
An empty loadouts install regenerates Codex config, so upstream-only MCP entries
are lost. Claude's installer writes `.claude.json`; loadouts instead owns the
portable server entry in the project's `.mcp.json`.

Tests use temporary HOME, fake skills, and a fake installer; real acceptance uses
temporary projects and isolated CBM runtime/cache. No network, global user-config
changes, new dependencies, or publication. Reuse the existing feat/cli branch.

## Acceptance results — 2026-11-04

Tested on Linux with Bun 1.4.4 and the existing codebase-memory-mcp 0.12.1
executable. The actual loadouts CLI selected the integration for both harnesses
in a temporary Git project, with an isolated HOME, CBM runtime and cache. Skills
inventory used the test fixture; configuration and indexing used the real CBM
executable. The native CLI was never copied, upgraded or globally reconfigured.

- First install produced both harnesses' skills, three agent profiles, hooks and
  MCP configuration. Both MCP reachability checks passed.
- Second install reported `Nothing changed.` Every project file retained its
  bytes and modification timestamp.
- Real `cli list_projects` returned the temporary project's absolute path.
- Deleting the Codex profile and reinstalling restored its original bytes and
  reported the repair.
- Real `codex mcp list --json` read the generated home and listed the server.
  An automated launcher test also checks that regeneration preserves MCP/hooks.
- Removing the selection removed owned project assets and the MCP entries.
  Real `cli list_projects` still returned the project afterwards.
- The existing binary's modification timestamp stayed unchanged. No harness
  configuration was created in the temporary HOME outside the managed project.

The final run's logs and assertions are under
`/tmp/loadouts-cbm-live-znrwlzc9/` (`summary.json`, `install-first.txt`,
`install-second.txt`, `projects.txt`, `repair.txt`, `codex-mcp.txt`, `remove.txt`,
`projects-retained.txt`). Temporary evidence may be cleaned up later; this section
records the outcomes. The harness emitted nonfatal warnings about temporary
directory permissions and Codex refusing to create PATH helpers under `/tmp`.
Unix sockets were blocked in the execution sandbox, so this isolated acceptance
ran with filesystem/network escalation. It made no real HOME configuration changes.

Interactive hook execution/trust and the dashboard UI were not exercised. Index
visibility was verified through the real CLI. No claims of cross-platform native
installer compatibility or exact shared-service version pinning are made.

Fresh review found that resolving a PATH symlink before native configuration
could put nonexistent executable paths in Codex profiles. A regression failed
with a renamed target, then passed after preserving the PATH executable location.
A second real run through that symlink repeated all acceptance checks and verified
the executable path in each of the three profiles. Evidence is under
`/tmp/loadouts-cbm-live-qoi7bdep/`. No other material review findings remained.
